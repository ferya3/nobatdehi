# معماری سیستم نوبت‌دهی بارگیری کامیون

سند مرجع معماری برای سامانه‌ی نوبت‌دهی و مدیریت صف بارگیری کارخانه.

- وضعیت: پیش‌نویس ۱ (قبل از شروع کدنویسی)
- دامنه: پنل راننده، پنل اپراتور/نگهبانی/باسکول، پنل مدیریت و داشبورد مدیرعامل
- رویکرد: Monolithic Modular Laravel (نه Microservice)

## 2. بخش‌های اصلی سیستم

سیستم به ۵ بخش اصلی تقسیم می‌شود:

| بخش | کاربر | کارکرد |
|---|---|---|
| A. پنل راننده | راننده | ورود با OTP، ثبت کامیون، دریافت نوبت، مشاهده وضعیت |
| B. پنل اپراتور | اپراتور صف | مدیریت صف Real-Time، تغییر وضعیت نوبت‌ها |
| C. صفحه ورود/نگهبانی/باسکول | نگهبان، باسکول | اعتبارسنجی نوبت، Check-in، ثبت وزن |
| D. پنل مدیریت کارخانه | مدیر کارخانه، Super Admin | ظرفیت، محصولات، کاربران، تنظیمات، گزارش |
| E. داشبورد مدیرعامل | مدیرعامل | فقط KPI و گزارش (بدون دسترسی عملیاتی) |

### A. پنل راننده

اپلیکیشن نصب‌شونده نمی‌سازیم؛ در فاز اول **PWA / Web App**:

```
factory.ir/queue
```

مسیر راننده:

```
شماره موبایل → OTP → ورود → ثبت کامیون → نوع بار → تاریخ → دریافت نوبت
```

## 3. پنل و فرآیند راننده

### 3.1 صفحه اول

```
┌──────────────────────────┐
│        لوگوی کارخانه      │
│                          │
│       نوبت بارگیری       │
│                          │
│ شماره موبایل             │
│ ┌──────────────────────┐ │
│ │ 09xxxxxxxxx          │ │
│ └──────────────────────┘ │
│                          │
│      [ دریافت کد ]       │
└──────────────────────────┘
```

### 3.2 OTP

```
کد ارسال شده را وارد کنید
[  _  _  _  _  _  ]
ارسال مجدد 00:42
```

### 3.3 اطلاعات کامیون

```
شماره پلاک
[ ایران ] [ 12 ] [ 345 ] [ 67 ]

نوع خودرو
○ تک   ○ جفت   ○ تریلی   ○ خاور   ○ کامیون

نام راننده
شماره موبایل
```

اگر راننده قبلاً ثبت شده باشد، اطلاعاتش از دیتابیس خوانده و فرم Pre-fill می‌شود.

### 3.4 انتخاب نوع بار

```
┌───────────────────┐      ┌───────────────────┐
│ محصول A           │      │ محصول B           │
│ بارگیری: 30 تن    │      │ بارگیری: 20 تن    │
└───────────────────┘      └───────────────────┘
```

فهرست محصولات و ظرفیت بارگیری هر کدام باید از پنل مدیریت قابل تغییر باشد (بدون Deploy).

**پیاده‌سازی:** `/panel/products` (دسترسی `products.manage`) — افزودن، تغییر نام، تناژ،
مدت بارگیری، ترتیب نمایش و فعال/غیرفعال کردن. محصولی که در نوبت‌های ثبت‌شده به کار
رفته حذف نمی‌شود (کلید خارجی `restrictOnDelete`)؛ پنل به‌جای خطای پایگاه داده،
غیرفعال کردن را پیشنهاد می‌دهد.

### 3.4.1 انواع کامیون و زمان‌بندی آن‌ها

هر نوع کامیون دو عدد زمانی دارد که موتور صف را تغذیه می‌کند:

| ستون | معنی | اگر خالی باشد |
|---|---|---|
| `loading_minutes` | مدت معمول بارگیری این نوع | از `products.loading_minutes` و بعد `factories.avg_loading_minutes` |
| `grace_minutes` | مهلت حضور بعد از شروع ساعت نوبت | از `factories.no_show_grace_minutes` |

این دو عدد تزئینی نیستند:

- **تخمین انتظار** دیگر «تعداد نفرات جلوتر × یک میانگین ثابت» نیست؛ مجموع
  `loading_minutes` کامیون‌های جلوتر است. یک تریلی جلوی صف، تخمین را بیشتر از یک
  خاور جابه‌جا می‌کند.
- **آزادسازی ظرفیت** با `appointments:no-show` که هر پنج دقیقه اجرا می‌شود: نوبتی که
  `start_time + grace_minutes` آن گذشته و کامیون نیامده، «عدم حضور» می‌خورد و
  `reserved_count` اسلات آزاد می‌شود. `appointments:expire` شبانه است و برای اداره‌ی
  صفِ همان روز دیر می‌رسد.

**پیاده‌سازی:** `/panel/truck-types` (همان دسترسی `products.manage`).

### 3.5 UX Flow کامل راننده

```
ورود → شماره موبایل → OTP → اطلاعات کامیون → نوع بار
   → انتخاب تاریخ → انتخاب ساعت → تأیید → شماره نوبت
   → QR → SMS Confirmation → مراجعه به کارخانه
   → QR Scan → Check-in → انتظار → فراخوان → بارگیری → پایان
```

### 3.6 پیگیری وضعیت نوبت توسط راننده

راننده با شماره موبایل + OTP وضعیت لحظه‌ای را می‌بیند:

```

#128

وضعیت: 🟡 در انتظار
تعداد خودروهای قبل از شما: 4
زمان تقریبی: 35 دقیقه
```

و به‌صورت Real-Time:

```

```

این قابلیت بخش بزرگی از تماس‌های تلفنی با کارخانه را حذف می‌کند.

## 5. چرخه وضعیت نوبت (State Machine)

مسیر اصلی:

```
BOOKED
   ↓
WAITING
   ↓
CALLED
   ↓
CHECKED_IN
   ↓
LOADING
   ↓
LOADED
   ↓
COMPLETED
```

وضعیت‌های استثنا:

```
CANCELLED
NO_SHOW
REJECTED
EXPIRED
```

قوانین:

- انتقال وضعیت فقط از طریق Action مجاز انجام شود، نه `update(['status' => ...])` پراکنده در Controller.
- بازگشت به عقب (مثلاً `LOADING → BOOKED`) فقط با Permission ویژه و حتماً با Audit Log.
- هر انتقال با `changed_by`, `changed_at`, `reason` ثبت شود — این داده بعداً ستون فقرات گزارش‌گیری است.

```
│ #127   65-982-43    محصول A    بارگیری      10:25        │
│ #128   21-123-55    محصول A    منتظر        10:30        │
└──────────────────────────────────────────────────────────┘
```

### 6.2 Real-Time

```
                    نوبت جدید
                       ↓
                  WebSocket (Reverb)
                       ↓
              ┌───────────────┐
              │ Operator Panel│
              └───────────────┘
                       ↓
                 نمایش #128
```

پیاده‌سازی: **Laravel Reverb + Redis** — نه Ajax Polling که هر چند ثانیه دیتابیس را بکشد.

کانال‌ها (خصوصی/Presence):

- `private-factory.{factory_id}.queue` — تغییرات صف
- `private-factory.{factory_id}.dashboard` — شمارنده‌های داشبورد
- `private-driver.{driver_id}` — وضعیت نوبت راننده
- `private-factory.{factory_id}.gate` — رویدادهای نگهبانی

### 6.3 دکمه‌های اپراتور

```
[ فراخوانی ]  [ ورود به محوطه ]  [ شروع بارگیری ]  [ پایان بارگیری ]
[ عدم حضور ]  [ لغو ]           [ مشاهده جزئیات ]
```

UX باید جلوی خطا را بگیرد: دکمه‌ای که در وضعیت فعلی مجاز نیست، اصلاً فعال نباشد. اعتبارسنجی هم در UI و هم در Backend (Policy + State Machine) انجام شود.

### 6.4 زنجیره‌ی فیزیکی و نقاطی که قفل می‌شوند

کامیون از پنج ایستگاه رد می‌شود و در هر ایستگاه یک چیز اثبات می‌شود. طراحی
عمدی این است که هر قفل در **سرور** باشد، نه در UI: دکمه‌ای که خاکستری است ولی
درخواستش را بشود دستی فرستاد، قفل نیست.

| ایستگاه | چه چیزی اثبات می‌شود | چه چیزی قفل است |
|---|---|---|
| ۱. پیش‌ثبت‌نام | کد ملی (با رقم کنترل)، پلاک، نوع بار | حواله و QR امضاشده صادر می‌شود |
| ۲. گیت | راننده QR دارد و پلاکش با حواله یکی است | بدون بلیط اسکن، `check-in` رد می‌شود |
| ۳. باسکول اول | وزن خالی، با منبع و عکس | بدون آن، بارگیری شروع نمی‌شود |
| ۴. لاین بارگیری | اسکن همان QR روی لاین | زمان ثبت و تأخیر هشدار داده می‌شود |
| ۵. باسکول دوم | وزن پر ⇒ خالص = پر − خالی | مغایرت یا اضافه‌بار ⇒ برگه‌ی خروج صادر نمی‌شود |

**یک QR برای تمام مسیر.** توکن در گیت مصرف نمی‌شود؛ راننده همان کد را در لاین
و باسکول هم نشان می‌دهد و هر ایستگاه از روی *وضعیت نوبت* می‌فهمد این اسکن چه
معنایی دارد. تکرارِ یک مرحله را وضعیت می‌بندد، نه سوزاندن توکن.

**بلیط اسکن (`ScanTicket`).** اسکن موفق در گیت یک کلید کوتاه‌عمر در session
همان ایستگاه می‌گذارد و `check-in` بدون آن رد می‌شود. بدون این، «بدون QR ورود
ممنوع» فقط یک جمله در UI بود و یک `POST` خام دورش می‌زد.

**تطبیق پلاک.** اگر پلاک‌خوان مقداری فرستاده باشد، سرور خودش مقایسه می‌کند و
تأیید چشمیِ نگهبان اصلاً خوانده نمی‌شود — دستگاه تبانی نمی‌کند.
`PlateNumber::normalizeKey()` فرمت‌های مختلف دستگاه‌ها («۱۲ب۳۴۵ایران۶۷»،
«12 ب 345 - 67») را به یک کلید می‌رساند، وگرنه هر خواندنِ درست هم «مغایرت»
می‌شد و قانون بی‌اثر.

**استثنای ورود.** دسترسی `gate.manual-override` جدا از `queue.checkin` است:
نگهبان می‌تواند ورود ثبت کند ولی فقط با اسکن. دور زدن این قانون کارِ مدیر
است، دلیل کتبی می‌خواهد، و در `security_logs` می‌نشیند.

**وزن خالص هرگز وارد نمی‌شود.** `WeighingService` آن را از پر منهای خالی حساب
می‌کند. هر توزین یک بار ثبت می‌شود؛ «اصلاح» وزن خالی بعد از بارگیری بسته است،
چون دقیقاً همان حفره‌ای است که وزن خالص را دلخواه می‌کند.

**ترتیب مرحله‌ها.** `TransitionPreconditions` شروع بارگیری را بدون توزین خالی و
ثبت خروج را بدون برگه‌ی خروج رد می‌کند. بازگردانی عمداً معاف است: کارِ اصلاحِ
اشتباه نباید پشت همان شرطی گیر کند که اشتباه را ساخته.

### 6.5 اولویت و اعلام زمان

**اولویت فقط داخل یک ساعت اثر دارد.** `scopeQueueOrder()` به ترتیب
`start_time`، بعد `priority` نزولی، بعد `number` مرتب می‌کند. اگر اولویت قبل
از ساعت می‌آمد، نوبت ساعت ۱۴ می‌توانست جلوی نوبت ساعت ۸ بیفتد و کل نوبت‌دهی
بی‌معنی می‌شد.

اولویت دو منبع دارد:

- `products.priority` — پیش‌فرضِ هر محصول (مثلاً بار صادراتی)، از پنل محصولات.
- `appointments.priority` — snapshot لحظه‌ی ثبت، که اپراتور با دسترسی
  `queue.manage` می‌تواند عوض کند. **دلیل اجباری است** و در Audit Log
  می‌نشیند؛ «چرا این کامیون جلو افتاد» باید بعداً قابل جواب دادن باشد.

snapshot عمدی است: تغییر اولویت یک محصول نباید ترتیب صفِ دیروز را عوض کند.

**زمان همان لحظه‌ی ثبت اعلام می‌شود.** `QueueService::plannedSchedule()`
برخلاف `estimatedWaitMinutes()` که فقط برای امروز معنی دارد، برای نوبت فردا
هم کار می‌کند:

```
تخمین شروع = ساعت نوبت + (مجموع مدت بارگیریِ نوبت‌های جلوتر ÷ تعداد لاین)
تخمین پایان = تخمین شروع + مدت بارگیریِ نوعِ همین کامیون
```

راننده این را در سه جا می‌بیند: روی کارتِ انتخاب نوع خودرو («تریلی ≈ ۴۰
دقیقه»)، در مرحله‌ی تأیید، و در پیامک تأیید نوبت.

> **ساعت‌ها روی سرور فرمت می‌شوند، نه در مرورگر.** فرستادن ISO و تبدیل با
> `new Date()` یعنی گوشیِ راننده‌ای که منطقه‌ی زمانی‌اش روی UTC مانده،
> ۰۷:۰۰ را ۰۳:۳۰ نشان می‌دهد. بقیه‌ی سامانه هم همین کار را می‌کند.

### 6.6 چه کسی نوبت را بست

هر نوبتی که به وضعیت پایانیِ ناموفق می‌رسد (`CANCELLED`، `REJECTED`، `NO_SHOW`،
`EXPIRED`)، هویت عاملش را روی خودِ نوبت نگه می‌دارد:
`cancelled_by_type` (`driver` | `staff` | `system`) و `cancelled_by_name`.

`appointment_transitions` همین اطلاعات را دارد، ولی صف و گزارش نباید برای هر سطر
تاریخچه بخوانند؛ این دو ستون کنار `cancel_reason` می‌نشینند و صف، جزئیات نوبت و
صفحه‌ی راننده همگی برچسبِ آماده را نشان می‌دهند: «لغو توسط راننده»، «لغو توسط
مریم احمدی»، «ثبت عدم حضور توسط سامانه».

بازگرداندن نوبت به یک وضعیت فعال، هر سه ستون را پاک می‌کند — وگرنه نوبتی که
اپراتور دوباره باز کرده تا ابد «لغو توسط راننده» را نشان می‌دهد.

### 7.2 مسیر QR

```

```

### 7.3 امنیت QR

QR **نباید** این باشد:

```
appointment_id=128
```

چون بی‌زحمت قابل جعل است. به‌جای آن:

```
QR Payload → Signed / Encrypted Token → Server Validation → Appointment
```

- توکن امضاشده (HMAC یا JWT کوتاه‌عمر) با `appointment_id`, `nonce`, `exp`
- تاریخ انقضا داشته باشد (مثلاً تا پایان روز نوبت)
- Token پس از Check-in یک‌بارمصرف شود (Replay Protection روی Redis)

### 7.4 دستگاه‌های گیت

سه دستگاه، هر سه اختیاری، و هیچ‌کدام قانون‌های بالا را شل نمی‌کنند.

| دستگاه | چه می‌کند | چطور وصل می‌شود |
|---|---|---|
| بارکدخوان | همان QR راننده را می‌خواند | USB/بلوتوث، خودش را کیبورد معرفی می‌کند |
| دوربین عکس پلاک | نگهبان از پلاک عکس می‌گیرد | وب‌کم یا دوربین تبلتِ ایستگاه |
| دوربین پلاک‌خوان | خودش پلاک را می‌خواند و می‌فرستد | `POST /api/gate/anpr` با توکن دستگاه |

**بارکدخوان.** درایور ندارد و رویداد اختصاصی هم ندارد؛ محتوای بارکد را
«تایپ» می‌کند و آخرش Enter می‌زند. تشخیصش فقط از روی سرعت است: فاصله‌ی
کمتر از ~۳۵ میلی‌ثانیه بین کلیدها یعنی دستگاه، بیشتر یعنی انگشتِ آدم.
تایپِ انسان بافر را دور می‌ریزد و وقتی مکان‌نما داخل یک input باشد، اصلاً
گوش نمی‌دهیم — وگرنه نگهبانی که دارد چیزی می‌نویسد سهواً ورود ثبت می‌کند.

**دوربین پلاک‌خوان.** تنها مسیر بی‌session سامانه است، پس:

- تا در تنظیمات فعال نشده باشد، مسیر ۴۰۴ می‌دهد — وجودِ مسیر هم اطلاعات است
- توکن با `hash_equals` مقایسه می‌شود، نه `===`
- هر تلاش ناموفق در لاگ امنیتی می‌نشیند
- محتوایی که با هیچ امضای تصویری شروع نشود روی دیسک نوشته نمی‌شود

**ترتیب مراجع در تطبیق پلاک** (`PlateVerifier`) از بالا به پایین:

```
خواندنِ دوربین  →  رشته‌ی پلاکِ دستگاه  →  تأیید چشمی نگهبان
```

دستگاه بالاتر از نگهبان است چون تبانی نمی‌کند. ولی سه حالت، تصمیم را به
نگهبان برمی‌گردانند و «مغایرت» حساب نمی‌شوند: دوربین نتوانست بخواند،
اطمینانش زیر آستانه بود، یا اصلاً خواندنی نفرستاد. فرقِ «دوربین پلاک دیگری
خواند» با «دوربین چیزی نخواند» همان مرزی است که اگر رعایت نشود، اولین شبِ
بارانی یا کل گیت را قفل می‌کند یا کل قانون را بی‌اثر.

خواندنِ کهنه استثناست: بیش از ۱۰ دقیقه یعنی رد، نه بازگشت به نگهبان —
وگرنه پلاکِ درستِ دیروز می‌توانست بی‌سروصدا راهبند امروز را باز کند.

**سابقه.** هر خواندن پلاک در `plate_readings` می‌ماند، چه به نوبتی وصل شود چه
نشود؛ دوربین کامیونِ بی‌نوبت و خواندنِ ناموفق را هم می‌بیند و دقیقاً همان‌ها
هستند که حراست بعد از یک حادثه دنبالشان می‌گردد. روی خودِ نوبت سه ستون
اضافه شده: `gate_scan_source` (دوربین مرورگر یا بارکدخوان)،
`gate_plate_source` (کدام مرجع پلاک را تأیید کرد) و `gate_plate_reading_id`
(عکسِ همان لحظه).

عکس‌ها روی دیسک **خصوصی** می‌نشینند و از مسیرِ دارای دسترسی سرو می‌شوند،
نه با لینک مستقیم — برخلاف عکس باسکول. عکسِ هر خودرویی که از جلوی دوربین رد
شده داده‌ی نظارتی است و نباید با دانستنِ آدرس برای همه باز باشد. خواندن‌هایی
که به نوبتی گره نخورده‌اند با `plate-readings:prune` بعد از مدت نگهداری پاک
می‌شوند؛ بایگانیِ عکسِ هر رهگذر برای همیشه، هم مشکل دیسک است هم مشکل حقوقی.

### 7.5 اتصال نشان‌دهنده‌ی باسکول

نشان‌دهنده HTTP بلد نیست؛ زبانش سریال است (RS232/USB-CDC). پلِ `bridge/scale/`
روی کامپیوترِ اتاقک اجرا می‌شود، پورت COM را می‌خواند و هر عدد را به
`POST /api/weighbridge/reading` می‌فرستد — همان الگوی دوربین پلاک‌خوان، با
همان مکانیزم توکن دستگاه (`DeviceTokens`) ولی توکن جدا.

**محدودیتی که معماری را تعیین می‌کند:** روی ویندوز یک پورت COM را دو برنامه
همزمان نمی‌توانند باز کنند. تا وقتی نرم‌افزار قبلیِ باسکول اجرا می‌شود، پل
پورت را نمی‌گیرد. یعنی این دو با هم کار نمی‌کنند؛ یکی باید کنار برود.

**`device` که واقعاً `device` باشد.** ستون‌های `tare_source`/`gross_source` از
اول مقدار `device` را می‌پذیرفتند، ولی معنایش «اپراتور در فرم تیک زد» بود —
عدد را خودش تایپ می‌کرد. حالا:

```
یا reading_id  →  سرور وزن را از همان ردیف برمی‌دارد و عددِ فرم را نمی‌خواند
یا ورود دستی   →  با دلیل کتبی، و فقط وقتی باسکول وصل است
```

حالت سومی نیست. اگر عدد از فرم خوانده می‌شد، «مستقیم از باسکول» دوباره به
یک رشته‌ی قابل تایپ برمی‌گشت.

سرور خواندن را رد می‌کند اگر:

| شرط | چرا |
|---|---|
| کهنه‌تر از ۹۰ ثانیه | وزن هر لحظه عوض می‌شود؛ شاید کامیون بعدی روی سکوست |
| مالِ کارخانه‌ی دیگر | همان قاعده‌ی خواندنِ پلاک |
| عقربه هنوز نوسان دارد | ثبت وزنِ ناپایدار هیچ ردی از خودش نمی‌گذارد |

شرط سوم قابل خاموش‌کردن است، چون همه‌ی نشان‌دهنده‌ها پرچم پایداری
نمی‌فرستند و اجبارِ آن روی چنین دستگاهی یعنی هیچ وزنی ثبت نمی‌شود.

**ورود دستی** بسته نمی‌شود — باسکول خراب می‌شود — ولی وقتی پل روشن است دلیل
کتبی می‌خواهد و در لاگ امنیتی می‌نشیند. وقتی پل خاموش است هیچ دلیلی خواسته
نمی‌شود: روی نصبی که باسکول متصل ندارد، تایپ‌کردن تنها راه است و پرسیدنِ
«چرا تایپ کردی» فقط فیلدی می‌سازد که با «test» پر می‌شود.

**سابقه.** هر عددی که پل بفرستد در `scale_readings` می‌ماند — حتی صفر، حتی
منفی، حتی ناپایدار. همان عددهای عجیب هستند که نشان می‌دهند باسکول یا کابل
مشکل دارد؛ فیلترکردنشان در لحظه‌ی دریافت یعنی مشکل را ندیدن. `raw_frame` هم
ذخیره می‌شود تا اگر پارسر اشتباه بخواند، بشود فهمید.

**آنچه معادل ندارد.** با کنار گذاشتن نرم‌افزار قبلیِ باسکول این‌ها از دست
می‌روند: قبض توزین با کد و بارکد خودش، «حق توزین»، کد پالت، کد انبار و کد
بخش، و توزینِ خودرویی که نوبت ندارد. عددِ توزینِ بی‌نوبت در `scale_readings`
ثبت می‌شود ولی به حواله‌ای گره نمی‌خورد و در `loading_records` جایی ندارد.

| نقش | دسترسی |
|---|---|
| Super Admin | همه چیز |
| مدیر کارخانه | گزارش + مدیریت (ظرفیت، محصولات، کاربران عملیاتی) |

## 13. همزمانی، Race Condition و Idempotency

### 13.1 مشکل

```
Request A → ظرفیت 1
Request B → ظرفیت 1

اگر طراحی درست نباشد:
A → قبول
B → قبول
ظرفیت = -1     ← فاجعه کوچک صنعتی
```

### 13.2 راه‌حل: Transaction + Lock + Constraint

```
BEGIN TRANSACTION
    SELECT ... FROM appointment_slots
      WHERE id = :slot FOR UPDATE          -- Row Lock
    IF reserved_count >= capacity → ROLLBACK / خطای «ظرفیت تکمیل»
    INSERT INTO appointments (...)
    UPDATE appointment_slots
      SET reserved_count = reserved_count + 1
      WHERE id = :slot
COMMIT
```

سه لایه دفاع:

1. `SELECT ... FOR UPDATE` روی ردیف Slot
2. `CHECK (reserved_count <= capacity)` در دیتابیس
3. Unique Constraint روی محدودیت‌های کسب‌وکار (مثلاً یک نوبت فعال به ازای هر پلاک)

### 13.3 Idempotency

اگر راننده سه بار روی «ثبت نوبت» کلیک کند، نباید سه نوبت صادر شود.

- کلاینت برای هر تلاش ثبت، یک `idempotency_key` (UUID) تولید و در Header ارسال می‌کند.
- سرور: اگر کلید تکراری بود، همان پاسخ قبلی برگردانده شود (نه ایجاد رکورد جدید، نه خطا).
- `UNIQUE(idempotency_key)` روی جدول تضمین نهایی است.
- دکمه‌ی Submit در UI بعد از اولین کلیک Disable شود (لایه‌ی اول، نه تنها لایه).

### 14.1 احراز هویت راننده

راننده Username/Password ندارد:

```

```

سیاست OTP:


- انقضا، محدودیت تعداد تلاش، محدودیت تعداد ارسال SMS.
- Rate Limit بر اساس IP **و** شماره موبایل.
- بعد از تأیید موفق، OTP باطل شود.

### 14.2 امنیت API

هر Endpoint Authorization جداگانه دارد:

```

/api/auth/verify-otp
/api/appointments
/api/appointments/{id}
/api/operator/queue
/api/operator/checkin

```

`if (auth())` و تمام — همان نوع امنیتی است که تا روز حادثه بسیار قانع‌کننده به نظر می‌رسد. به‌جای آن: Policy برای هر Resource، Form Request برای Validation، و API Resource برای خروجی (تا فیلد اضافه لو نرود).

### 14.3 Anti-Abuse

## 15. Notification و SMS

### 15.1 SMS نباید داخل Request اصلی باشد

اشتباه:

```
Driver → Laravel → Create Ticket → SMS API → Response
```

اگر SMS Provider کند شود، صدور نوبت هم کند می‌شود.

درست:

```
Driver
   ↓
Laravel
   ↓
Create Ticket
   ↓
Commit DB
   ↓
Response سریع به راننده
   ↓
Redis Queue
   ↓
SMS Worker
   ↓
SMS Provider
```

Job با Retry و Backoff، و در صورت شکست نهایی → `failed_jobs` + Alert.

### 15.2 پنل‌های پشتیبانی‌شده

`SmsManager` شش پنل را می‌شناسد و انتخاب پنل یک ردیف در جدول `settings` است:

| کلید | پنل |
|---|---|
| `afe` | عصر فرا ارتباط و نمایندگی‌ها (afe.ir، wide.ir، دامنه‌ی اختصاصی) |
| `kavenegar` | کاوه‌نگار |
| `smsir` | SMS.ir |
| `melipayamak` | ملی‌پیامک |
| `custom` | هر پنل دیگر، با لینک ارسال و متغیرهای `{to}` `{text}` `{from}` `{apikey}` |
| `console` | آزمایشی — فقط در `storage/logs/sms-test.log` می‌نویسد |

این پیاده‌سازی از پروژه‌ی `payroll-saas` پورت شده تا همان پنل پیامکی با همان
مشخصات در هر دو سامانه کار کند.

**تنظیمات در دیتابیس است، نه در `.env`.** عوض‌کردن پنل یا رمزش نباید نیاز به
دسترسی SSH و ری‌استارت سرویس داشته باشد. رمز پنل و کلید API با `Crypt`
رمزنگاری‌شده ذخیره می‌شوند و هرگز به Frontend یا Audit Log نمی‌روند.

### 15.3 محافظ SSRF

همه‌ی درخواست‌های بیرونی از `SafeHttp` عبور می‌کنند:

- فقط `http`/`https`
- نام میزبان پیش از اتصال حل و در برابر فهرست کامل شبکه‌های خصوصی بررسی می‌شود
- اتصال به همان IP بررسی‌شده پین می‌شود (ضد DNS-rebinding)
- ریدایرکت دنبال نمی‌شود

بدون این، «لینک پنل سفارشی» به یک ابزار آماده برای خواندن سرویس‌های داخلی
سرور تبدیل می‌شد.

### 15.4 نمونه پیام مدیرعامل

```
نوبت جدید بارگیری
شماره نوبت: 128
پلاک: 12-345-67
راننده: علی رضایی
نوع بار: محصول A
تاریخ: 1405/06/16
```

### 15.5 Notification فقط برای مدیرعامل نیست

| گیرنده | رویداد |
|---|---|

| مدیر کارخانه | گزارش پایان روز |

کانال‌ها: SMS، In-App (Notification Center)، و در فاز بعد Web Push.

## 22. Backup

```
Production
     ↓
Encrypted Backup
     ↓
Separate Storage (Off-site)
```

حداقل‌ها:

- Daily Full Backup + Point-in-Time Recovery (WAL Archiving)
- Backup روی همان سرور DB نباشد
- رمزنگاری در حالت At-Rest و در انتقال
- Retention مشخص (مثلاً ۷ روزانه، ۴ هفتگی، ۱۲ ماهانه)
- **Restore را تست کن.** Backupای که هیچ‌وقت Restore نشده، بیشتر یک امیدواری است تا Backup.

## 27. قدم بعدی

قبل از شروع کدنویسی، این چهار مورد باید دقیق شوند:

1. **Database Schema + ERD** — جدول‌ها، روابط، Constraintها، Indexها

4. **State Machine دقیق نوبت** — انتقال‌های مجاز و Permission هر انتقال

تغییر منطق صف در وسط پروژه تقریباً همان لذتی را دارد که تعویض موتور هواپیما هنگام پرواز.
