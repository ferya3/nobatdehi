# سامانه نوبت‌دهی بارگیری کامیون

سامانه‌ی نوبت‌دهی، مدیریت صف و بارگیری کامیون‌های کارخانه.

راننده با شماره موبایل و کد یک‌بارمصرف وارد می‌شود، نوبت می‌گیرد و کد QR
دریافت می‌کند؛ نگهبانی ورود را ثبت می‌کند؛ اپراتور صف را به‌صورت زنده اداره
می‌کند؛ مدیر ظرفیت را تنظیم و گزارش می‌گیرد.

## مستندات

- [معماری سیستم](docs/ARCHITECTURE.md) — معماری کلی، ماژول‌ها، دیتابیس، امنیت، Deployment

| Cache / Session / Queue | Redis |

| تاریخ | شمسی (morilog/jalali)، ساعت به وقت تهران |

## نصب روی سرور (Ubuntu 24.04)

```bash
BRANCH=claude/system-architecture-b9hlgv
BASE=https://raw.githubusercontent.com/ferya3/nobatdehi/$BRANCH

curl -fsSL -o install.sh      "$BASE/install.sh"
curl -fsSL -o install.sh.sha256 "$BASE/install.sh.sha256"

sha256sum -c install.sh.sha256 || { echo 'اسکریپت دستکاری شده — اجرا نکنید'; exit 1; }

less install.sh                      # یک بار نگاهش کنید
sudo bash install.sh --domain factory.ir --email you@example.com
```

> **چرا `curl | sudo bash` نه.** آن دستور کدی را با دسترسی root اجرا می‌کند
> که هیچ‌کس ندیده و هیچ‌چیز تأییدش نکرده؛ اگر ریپو یا CDN یک بار دستکاری
> شود، کل سرور رفته است. `install.sh.sha256` کنار اسکریپت در همین ریپو است و
> با هر تغییر به‌روز می‌شود.

دامنه باید از قبل به IP سرور اشاره کند، وگرنه گرفتن گواهی HTTPS شکست می‌خورد
(بقیه‌ی نصب انجام می‌شود و بعداً می‌شود `sudo certbot --nginx -d factory.ir` زد).

اسکریپت PHP 8.4، PostgreSQL، Redis، Nginx و Node را نصب می‌کند، کد را می‌گیرد،
`.env` را با رمزهای تصادفی می‌سازد، مهاجرت‌ها را اجرا می‌کند، Frontend را build
می‌کند و سرویس‌های systemd (Reverb، Horizon، زمان‌بند) را بالا می‌آورد.
اجرای دوباره‌اش نصب را به‌روزرسانی می‌کند و رمزها و داده‌ها را دست نمی‌زند.

| گزینه | کار |
|---|---|
| `--domain factory.ir` | نام دامنه و فعال‌کردن HTTPS |
| `--email you@example.com` | ایمیل برای هشدارهای انقضای گواهی |
| `--no-tls` | بدون HTTPS (برای تست یا وقتی DNS آماده نیست) |
| `--branch main` | نصب از شاخه‌ی دیگر |
| `--demo` | ساخت صف نمونه برای امروز |
| `--skip-packages` | نصب بسته‌های سیستمی را رد کن (وقتی خودتان مدیریتشان می‌کنید) |

بعد از نصب حتماً رمز کاربران نمونه را عوض کنید و پنل پیامکی را از
`/panel/settings/sms` تنظیم کنید — تنظیمات پیامک در دیتابیس است، نه در `.env`.

## به‌روزرسانی سرور

```bash
curl -fsSL https://raw.githubusercontent.com/ferya3/nobatdehi/claude/system-architecture-b9hlgv/update.sh \
  | sudo bash
```

**`git pull` به‌تنهایی روی این سرور هیچ اثری ندارد.** سه چیز جلویش را می‌گیرند:

1. **opcache با `validate_timestamps = 0`** نصب شده (برای سرعت). PHP-FPM فایلِ
   عوض‌شده را اصلاً دوباره نمی‌خواند تا وقتی ری‌استارت شود — یعنی سرور همچنان
   کد قدیمی را اجرا می‌کند.
2. **`route:cache`** فعال است. مسیر جدید تا وقتی کش دوباره ساخته نشود وجود
   ندارد و صفحه‌ی تازه ۴۰۴ می‌دهد.
3. **دارایی‌های Vite هش‌دارند.** بدون `npm run build`، مرورگر همان جاوااسکریپت
   قبلی را می‌گیرد.

`update.sh` هر سه را انجام می‌دهد، مهاجرت‌ها و seedهای بی‌خطر را اجرا می‌کند،
سرویس‌ها را ری‌استارت می‌کند و آخرش بررسی می‌کند که واقعاً اعمال شده باشد.

| گزینه | کار |
|---|---|
| `--branch <name>` | به‌روزرسانی از شاخه‌ی دیگر |
| `--skip-build` | ساخت frontend را رد کن (وقتی فقط تغییر backend داده‌اید) |

یک قدم دستی می‌ماند: Service Worker پنل راننده فایل‌های `/build/` را کش می‌کند،
پس یک بار `Ctrl+Shift+R` در مرورگر لازم است.

## تغییر دامنه

روی نصبی که از قبل کار می‌کند — مثلاً وقتی از IP به یک دامنه‌ی واقعی می‌روید:

```bash
BASE=https://raw.githubusercontent.com/ferya3/nobatdehi/claude/system-architecture-b9hlgv
curl -fsSL -o set-domain.sh        "$BASE/set-domain.sh"
curl -fsSL -o set-domain.sh.sha256 "$BASE/set-domain.sh.sha256"
sha256sum -c set-domain.sh.sha256 && sudo bash set-domain.sh --domain example.ir --email you@example.com
```

**`install.sh` را دوباره اجرا نکنید.** در پایانش `db:seed` کامل می‌زند و
`FactorySeeder` با `updateOrCreate` ساعات کاری، ظرفیت، تعداد لاین و محصولات را
به پیش‌فرض برمی‌گرداند — یعنی هرچه از پنل تنظیم کرده‌اید پاک می‌شود.

`set-domain.sh` فقط دامنه را عوض می‌کند: `server_name` در Nginx، گواهی HTTPS،
`APP_URL` و `VITE_REVERB_*`، بعد `npm run build` و ری‌استارت سرویس‌ها. به داده
دست نمی‌زند.

| گزینه | کار |
|---|---|
| `--domain <name>` | دامنه‌ی جدید (اجباری) |
| `--email <addr>` | ایمیل ثبت گواهی Let's Encrypt |
| `--no-tls` | بدون HTTPS |
| `--cloudflare` / `--no-cloudflare` | تشخیص خودکار پروکسی Cloudflare را دستی کن |

### پشت Cloudflare

اگر رکورد DNS «ابر نارنجی» باشد، اسکریپت خودش تشخیص می‌دهد و رنج‌های IP
کلادفلر را به `TRUSTED_PROXIES` اضافه می‌کند. بدون آن، Laravel آدرس کلادفلر را
IP کاربر می‌بیند و **همه‌ی** درخواست‌ها از یک IP شمرده می‌شوند — یعنی
rate limit و لاگ امنیتی بی‌اثر می‌شوند.

دو چیز را خودتان باید در پنل کلادفلر درست کنید:

- **SSL/TLS → Full (strict)**. روی `Flexible`، ریدایرکت HTTPS این سرور یک حلقه‌ی
  بی‌پایان می‌سازد و سایت اصلاً باز نمی‌شود.
- **Network → WebSockets** روشن باشد، وگرنه صف زنده به‌روز نمی‌شود و پنل به
  polling هر ۲۰ ثانیه می‌افتد.

## راه‌اندازی محلی

```bash
composer install
npm install
cp .env.example .env
php artisan key:generate
```

`.env` را برای PostgreSQL و Redis تنظیم کنید، سپس:

```bash
php artisan migrate --seed     # نقش‌ها، کارخانه‌ی نمونه، کاربران، قالب پیامک
php artisan slots:generate     # ساخت اسلات‌های ظرفیت افق نوبت‌دهی
php artisan db:seed --class=DemoQueueSeeder   # صف نمونه‌ی امروز (اختیاری)
```

چهار فرآیند برای اجرای کامل:

```bash
php artisan serve              # وب
php artisan reverb:start       # WebSocket
php artisan horizon            # کارگر صف (یا: php artisan queue:work)
npm run dev                    # Vite
```

### کاربران نمونه

رمز هر کاربر هنگام `db:seed` به‌طور تصادفی ساخته و **فقط همان یک بار** چاپ
می‌شود. روی سرور، `install.sh` آن را در `/etc/nobatdehi/initial_passwords`
(فقط برای root خواندنی) نگه می‌دارد.

اگر رمزی گم شد، رمز تازه بسازید:

```bash
php artisan user:password                       # فهرست کاربران
php artisan user:password admin@example.test    # رمز تصادفی تازه
```

| نقش | ایمیل |
|---|---|
| مدیر ارشد سامانه | admin@example.test |
| مدیر کارخانه | manager@example.test |
| اپراتور | operator@example.test |
| نگهبانی | gate@example.test |
| باسکول | scale@example.test |
| انبار | warehouse@example.test |
| مدیرعامل | ceo@example.test |

در اولین ورود، تغییر رمز اجباری است.

راننده رمز ندارد؛ در محیط توسعه با `OTP_EXPOSE_IN_RESPONSE=true` کد ورود
روی صفحه نمایش داده می‌شود.

## نکات پیاده‌سازی

**نوبت را سامانه تعیین می‌کند، نه راننده.** کارخانه مطب دکتر نیست: راننده
ساعت انتخاب نمی‌کند، در صف می‌ایستد. سه چیز می‌دهد — خودرو، بار، هویت — و
سامانه در جواب می‌گوید نوبتش کِی است.

اولین نوبتِ هر روز از ساعت باز شدن کارخانه (یا «همین حالا + مهلت رسیدن»،
هر کدام دیرتر) شروع می‌شود و هر نوبت بعدی از جایی که نوبت قبلی روی همان
لاین تمام شده. مدت هر نوبت از `truck_types.loading_minutes` می‌آید؛ تریلی
و خاور یک اندازه جا نمی‌گیرند.

کارخانه‌ای که چند لاین بارگیری دارد، چند کامیون را هم‌زمان می‌برد: هر نوبت
روی لاینی می‌نشیند که زودتر آزاد می‌شود. ساعتِ اعلام‌شده روی مضرب پنج دقیقه
رُند می‌شود (به بالا) و بعداً جابه‌جا نمی‌شود — نوبتی که لغو شود جای خالی‌اش
همان‌جا می‌ماند و بعدی‌ها جلو نمی‌افتند، وگرنه راننده‌ای که پیامکِ «۱۰:۲۰»
گرفته کامیونش را از دست می‌دهد.

**همزمانی.** دو کامیون هم‌زمان روی یک لاین با دو لایه جلوگیری می‌شود: قفل
advisory روی نوبت‌گیریِ کارخانه (که زمان‌بند را همیشه با صفِ کامل روبه‌رو
می‌کند)، و `UNIQUE (factory_id, date, line_no, start_time)` در خود
PostgreSQL. لایه‌ی دوم نباید هرگز فعال شود؛ اگر شد یعنی لایه‌ی اول دور زده
شده است.

**اولویت.** با زمان‌بندی سریالی، دو نوبت فقط وقتی ساعت یکسان دارند که روی
دو لاین موازی نشسته باشند — و اولویت دقیقاً همان‌جا تصمیم می‌گیرد. روی
کارخانه‌ی تک‌لاین عملاً بی‌اثر است، چون هر نوبت ساعت خودش را دارد.

**زنجیره‌ی ایستگاه‌ها.** کامیون از پنج ایستگاه رد می‌شود و هر قفل در سرور
است، نه در UI:

| ایستگاه | مسیر | قفل |
|---|---|---|
| گیت | `/panel/gate` | بدون بلیط اسکن QR، ورود ثبت نمی‌شود؛ مغایرت پلاک یعنی رد |
| باسکول اول | `/panel/weighbridge` | بدون وزن خالی، بارگیری شروع نمی‌شود |
| لاین بارگیری | `/panel/loading` | شروع فقط با اسکن حواله؛ تأخیر هشدار می‌گیرد |
| باسکول دوم | `/panel/weighbridge` | خالص = پر − خالی؛ مغایرت یا اضافه‌بار ⇒ بدون برگه‌ی خروج |
| خروج | `/panel/queue` | بدون برگه‌ی خروج، وضعیت «تکمیل» ثبت نمی‌شود |

راننده یک QR دارد و همان را در هر سه ایستگاه نشان می‌دهد؛ هر ایستگاه از روی
وضعیت نوبت می‌فهمد این اسکن چه معنایی دارد.

**وقتی هیچ اسکنری کار نمی‌کند.** نگهبانی و باسکول هر دو جستجوی پلاک دارند،
ولی معنایشان یکی نیست. در گیت، جستجوی پلاک فقط وضعیت را نشان می‌دهد و
دکمه‌ی ورود رویش خاموش است — راهی که «وقتی QR خوانده نمی‌شود» باز گذاشته
شود، همان راهی است که کامیون بی‌حواله از آن وارد می‌شود.

در باسکول این محدودیت لازم نیست: ثبت وزن از اول هم به بلیط اسکن نیاز نداشته
و آنچه وزن را نگه می‌دارد جای دیگری است — ترتیب مرحله‌ها، عددی که از خودِ
نشان‌دهنده می‌آید، و مغایرتی که برگه‌ی خروج را قفل می‌کند. پس پیدا کردنِ
حواله از راه پلاک هیچ اختیار تازه‌ای نمی‌دهد و باسکول با خرابیِ بارکدخوان
نمی‌ایستد. اگر یک کامیون دو حواله‌ی امروز داشته باشد، آنکه واقعاً کار
باسکول دارد جلو می‌افتد.

**به‌روزرسانی زنده‌ی پنل.** خبرِ نوبت تازه و تغییر وضعیت از listener‌های
**صف‌نشده** می‌آید و `QueueChanged` هم `ShouldBroadcastNow` است — یعنی
خوابیدنِ Horizon پنل را کور نمی‌کند (فقط پیامک عقب می‌افتد). اگر WebSocket
هم در دسترس نباشد، پنل هر ۲۰ ثانیه تازه می‌شود و همین را کنار عنوان صف
نشان می‌دهد: «زنده» یا «هر ۲۰ ثانیه».

**سخت‌سازی امنیتی.** `TRUSTED_PROXIES` پیش‌فرض فقط همین ماشین است (نه `*`)،
نشست رمزنگاری می‌شود، توکن دستگاه فقط از هدر خوانده می‌شود، Reverb روی
لوپ‌بک است، Redis رمز دارد، و هدرهای CSP/HSTS/Permissions-Policy از کد
می‌آیند نه از Nginx.

کاربران پنل با **رمز تصادفی** ساخته می‌شوند (یک بار موقع نصب چاپ می‌شود) و
تا عوضش نکنند هیچ صفحه‌ای باز نمی‌شود. `security:alert` هر ۱۵ دقیقه الگوهای
مشکوک لاگ امنیتی را به مدیران پیامک می‌کند.

**ساعت سرور.** `APP_TIMEZONE=Asia/Tehran`. ساعت‌ها روی سرور به `H:i` تبدیل
می‌شوند و نه به‌صورت ISO فرستاده — گوشی‌ای که روی UTC مانده باشد، ۰۷:۰۰ را
۰۳:۳۰ نشان می‌دهد.

**استثنای گیت.** `gate.manual-override` دسترسی جداگانه‌ای است که نگهبان
ندارد و مدیر کارخانه دارد. استفاده‌اش دلیل کتبی می‌خواهد و در لاگ امنیتی
ثبت می‌شود.

**دستگاه‌های میدانی.** چهار دستگاه اختیاری، از `/panel/settings/devices`:

| دستگاه | کار |
|---|---|
| بارکدخوان | همان QR راننده را می‌خواند؛ لازم نیست نگهبان جایی کلیک کند |
| دوربین عکس پلاک | عکسِ پلاک در سابقه می‌ماند، حتی وقتی راهبند باز نشود |
| دوربین پلاک‌خوان | خودش پلاک را می‌خواند و به `POST /api/gate/anpr` می‌فرستد |
| باسکول | پل، پورت COM را می‌خواند و وزن را به `POST /api/weighbridge/reading` می‌فرستد |

بارکدخوان درایور نمی‌خواهد: این دستگاه‌ها خودشان را کیبورد معرفی می‌کنند و
صفحه از روی سرعتِ تایپ تشخیصشان می‌دهد (زیر ۳۵ میلی‌ثانیه بین کلیدها).
وقتی مکان‌نما داخل یک فیلد باشد گوش نمی‌دهد، تا تایپِ نگهبان سهواً ورود ثبت
نکند.

دوربین پلاک‌خوان با توکن دستگاه احراز می‌شود (هدر `X-Gate-Token`) و تا در
تنظیمات فعال نشده باشد مسیرش ۴۰۴ می‌دهد. آدرس و توکن را همان صفحه‌ی
تنظیمات می‌دهد، و ۲۰ خواندن آخر را هم نشان می‌دهد — «دوربین وصل است؟» با
تیکِ تنظیمات جواب داده نمی‌شود.

**ترتیب مراجع پلاک.** `دوربین ← رشته‌ی دستگاه ← تأیید چشمی نگهبان`. دستگاه
بالاتر از نگهبان است چون تبانی نمی‌کند؛ ولی وقتی دوربین *نتوانسته* بخواند یا
اطمینانش زیر آستانه است، تصمیم به نگهبان برمی‌گردد و «مغایرت» ثبت نمی‌شود.
خواندنِ کهنه‌تر از ۱۰ دقیقه استثناست و رد می‌شود، وگرنه پلاکِ درستِ دیروز
راهبند امروز را باز می‌کرد.

عکس‌های پلاک روی دیسک خصوصی‌اند و از مسیر دارای دسترسی سرو می‌شوند، نه با
لینک مستقیم. خواندن‌هایی که به نوبتی گره نخورده‌اند بعد از مدت نگهداری
(پیش‌فرض ۳۰ روز) پاک می‌شوند.

**اتصال باسکول.** نشان‌دهنده HTTP بلد نیست؛ زبانش سریال است. پلِ
`bridge/scale/` روی کامپیوترِ اتاقک اجرا می‌شود، پورت COM را می‌خواند و هر
عدد را می‌فرستد. راهنمای نصب و عیب‌یابی در `bridge/scale/README.md` است.

روی ویندوز یک پورت COM را دو برنامه همزمان نمی‌توانند باز کنند؛ اگر
نرم‌افزار قبلی باسکول هنوز اجرا می‌شود، پل پورت را نمی‌گیرد.

**`device` حالا یعنی `device`.** قبلاً «مستقیم از باسکول» یک تیک در فرم بود
و عدد را همان اپراتور تایپ می‌کرد. حالا یا شناسه‌ی ردیفی از `scale_readings`
فرستاده می‌شود — که سرور وزنش را از همان ردیف برمی‌دارد و عددِ فرم را اصلاً
نمی‌خواند — یا ورود دستی است و وقتی باسکول وصل باشد، دلیل کتبی می‌خواهد و
در لاگ امنیتی می‌نشیند. حالت سومی نیست.

سرور خواندن را رد می‌کند اگر: کهنه باشد (بیش از ۹۰ ثانیه — وزن هر لحظه عوض
می‌شود)، مالِ کارخانه‌ی دیگری باشد، یا عقربه هنوز نوسان داشته باشد. آخری
قابل خاموش‌کردن است، چون همه‌ی نشان‌دهنده‌ها پرچم پایداری نمی‌فرستند.

**آنچه با کنار گذاشتن نرم‌افزار قبلیِ باسکول از دست می‌رود** و در این سامانه
معادل ندارد: قبض توزین با کد و بارکد خودش، «حق توزین»، کد پالت، کد انبار و
کد بخش، و توزینِ خودرویی که اصلاً نوبت ندارد. عددِ چنین توزینی در
`scale_readings` ثبت می‌شود ولی به حواله‌ای گره نمی‌خورد.

**اولویت و زمان.** ترتیب صف `ساعت → اولویت → شماره نوبت` است؛ اولویت جای
نوبت را فقط *داخل همان ساعت* جابه‌جا می‌کند. پیش‌فرضش از محصول می‌آید و
اپراتور با `queue.manage` و **دلیل کتبی** می‌تواند عوضش کند (در Audit Log).

مدت بارگیری از `truck_types.loading_minutes` می‌آید و راننده آن را همان
لحظه‌ی گرفتن نوبت می‌بیند — روی کارت انتخاب خودرو، در مرحله‌ی تأیید، در
پیامک، و در صفحه‌ی نوبت به‌صورت «تخمین شروع / تخمین پایان».

**کاتالوگ.** محصولات از `/panel/products` و انواع کامیون از `/panel/truck-types`
مدیریت می‌شوند (دسترسی `products.manage`). هر نوع کامیون دو عدد زمانی دارد:
`loading_minutes` که تخمین انتظارِ صف را می‌سازد و `grace_minutes` که مهلت حضور
راننده است. خالی گذاشتنشان یعنی «از محصول/کارخانه بگیر». بعد از پایان مهلت،
`appointments:no-show` ظرفیت را همان روز آزاد می‌کند.

**وضعیت نوبت.** تنها راه تغییر `status`، اکشن `TransitionAppointment` است.
انتقال‌های مجاز و بازگردانی‌ها در `AppointmentStateMachine` تعریف شده‌اند و
بازگردانی دسترسی جداگانه می‌خواهد.

**QR.** محتوای QR توکن امضاشده با HMAC است، نه شناسه‌ی نوبت. دیتابیس فقط
hash آن را نگه می‌دارد و بعد از ثبت ورود باطل می‌شود.

**پیامک.** هرگز داخل Request اصلی ارسال نمی‌شود؛ فقط یک ردیف
`sms_messages` ساخته و روی صف گذاشته می‌شود.

**پیامک لغو.** مدیر از هر دو طرف خبر می‌گیرد — چه راننده لغو کرده باشد چه
اپراتور — با ذکر اینکه چه کسی لغو کرده و چرا. شماره‌ها از
`/panel/settings/sms` خوانده می‌شوند. راننده فقط وقتی پیامک می‌گیرد که
خودش لغو نکرده باشد؛ پیامکِ «نوبتت لغو شد» به کسی که سه ثانیه پیش دکمه‌ی
لغو را زده، فقط اعتماد به پیامک‌های سامانه را کم می‌کند.

**Realtime.** WebSocket مسیر اصلی به‌روزرسانی است و polling فقط پشتیبان؛
با برقراری اتصال زنده، فاصله‌ی polling بلند می‌شود.
